一、本职工程能力（后端方向）：19 / 25

BE-1. 领域建模合理：4 / 5

评分项得分依据
数据模型设计4ConfigGroup（Service/Env/PublishedVersion/PublishedData/DraftData/LastPublishedAt）+ ChangeRecord（Time/Action/Key/Version/Operator）独立存储 + ConfigStore（Configs + Logs map）线程安全。DraftData/PublishedData 双数据模型是核心亮点，HasDraft() 数据驱动无冗余 Status 字段。扣 1 分：模型较简单，缺少多级隔离（Namespace）、配置格式类型、灰度标签等扩展预留。

BE-2. 分层架构设计：3 / 4

评分项得分依据
分层清晰度3main.go → handler/config.go → store/store.go 三层分离清晰。Handler 层仅处理 HTTP 请求/响应，Store 层集中数据模型和业务逻辑（SetKey/Publish/DeleteKey）。扣 1 分：Store 同时承担数据访问和业务逻辑，"SetKey 中判断 existed 决定 action 类型"这类逻辑可抽到独立的 Service 层，但 MVP 范围内可接受。

BE-3. API 设计清晰：4 / 5

评分项得分依据
API 设计48 个 REST 端点：资源型（GET /configs, GET /:service/:env）+ 命令型（POST /publish, PUT/DELETE /keys/:key）分离合理。区分前端消费（全量数据 + ChangeLog）和微服务消费（仅 PublishedData）接口。README 含完整 curl 示例和 8 接口一览表。扣 1 分：无分页/过滤参数、无 OpenAPI/Swagger 文档、错误响应格式在部分端点不一致（如 Publish 成功返回 message 而非结构化数据）。

BE-4. Draft/Published 生命周期：3 / 4

评分项得分依据
发布机制3【适配评分】本项目为配置中心而非工作项管理系统，用 DraftData→PublishedData 发布流程替代状态流转。实现：编辑写入 DraftData→Publish DeepCopy→PublishedData→Version 递增→微服务只读 PublishedData。DeepCopy 防止引用污染，HasDraft() 数据驱动状态，ChangeLog 记录每次操作。Publish 逻辑集中在 Store.Publish() 一个方法中，改动范围可控。扣 1 分：无发布前的校验钩子（如"必须非空才能发布"）、无回滚机制、无发布策略（如蓝绿/金丝雀）。

BE-5. 数据持久化与一致性：1 / 2

评分项得分依据
持久化1纯内存存储（ConfigStore struct + sync.RWMutex），无文件/数据库持久化。按评分表规则："仅内存存储但结构清楚、说明合理，本项最高 1 分"。sync.RWMutex 保证并发读写安全，读取用 RLock、写入用 Lock，并在并发测试中验证。

BE-6. 代码规范与质量：3 / 3

评分项得分依据
代码质量3命名一致（驼峰）、无通配符导入、无死代码。revive 12 issues + gofmt 1 diff 全部修复，go vet 通过。Package comment 完整、导出方法注释符合 Go 规范（Handler 方法注释格式正确）。无 AI 模板注释、无明显重复代码。单文件大小适中（最大 handler_test.go 464 行，合理）。

BE-7. 错误处理与边界条件：1 / 2

评分项得分依据
错误处理1基础错误处理到位：400 for invalid JSON body、200+empty config for non-existing 资源、demo-service 5 次重试 + 降级启动。扣 1 分：错误响应消息统一性可加强（部分返回 {"message":"ok"}，部分仅返回 data）；缺少 404 语义（不存在的服务返回 200+空数据是设计选择但非 REST 惯例）；无输入校验（service/env name 可为空字符串导致 :"" key）。

复盘面试建议问题

1. 数据模型设计
"你的 ConfigGroup 使用了 DraftData/PublishedData 双数据模型，这是怎么想到的？与 Nacos 直接修改即生效的设计相比，你的方案有什么优势和代价？如果新增一个'灰度发布'需求，ReleaseData/GrayData/BaseData 三层数据，模型怎么改？"
2. 并发与一致性
"你的 ConfigStore 使用 sync.RWMutex 做并发控制。如果有两个管理员同时编辑同一配置组的同一个 Key，当前代码会怎么处理？如果你要把 publish 操作扩展为'审核 → 批准 → 发布'三步，如何保证一致性？"
3. AI 使用策略
"AI_PROMPTS 里你标注了每个模块的 AI 完成度（85%-100%）。哪些模块你让 AI 生成后基本没改？哪些模块你花了最多人工修正？BUG-007（Vue script 作用域问题）是你自己发现的还是 lint/build 发现的？如果让你重新用 AI 做这个项目，你会怎么规划 Prompt 策略？"
4. 配置推送实现
"你提到 /push 和 /watch 是预留接口。如果现在要求你实现配置变更后实时推送给所有订阅的微服务，你会选择 SSE、WebSocket 还是长轮询？请说明你的选型理由和关键实现挑战。"
5. 配置版本回滚
"你的 BumpVersion() 是递增补丁号，如果发布了一个错误配置（比如 db.url 写成了不存在的地址），你怎么让微服务回滚到上一个版本？当前模型是否支持？如果不支持，你打算加什么字段和接口？"
